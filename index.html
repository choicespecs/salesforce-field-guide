    Salesforce Field Guide

    Salesforce is a database with an application server, a security model, an automation engine and a UI framework bolted on top, all configured through metadata. Learn those pieces in order and the rest of the platform starts to make sense.

    Chapter 01

    Start here: a learning path

    Two tracks share the same foundation. Admins configure the platform with clicks; developers extend it with code. Everyone needs the first three weeks.

    Do this first: sign up for a free Developer Edition org at developer.salesforce.com/signup and a Trailhead account. Every concept in this guide is something you can click through in your own org in a few minutes.
    Chapter 02

    The mental model

    Six ideas explain most of how Salesforce behaves, including the parts that surprise people coming from regular web development.

    1. It's multi-tenant

    Thousands of customers share the same servers and database. Your company's slice is an org. Because you share resources, the platform enforces governor limits on every transaction so no tenant can starve the others.

    2. Everything is metadata

    Objects, fields, page layouts, flows, Apex classes and permissions are all metadata: descriptions the platform interprets at runtime. You don't run migrations; you deploy metadata. That's what makes clicks and code interchangeable.

    3. Objects are tables

    An object is a table, a field is a column, a record is a row. Custom ones end in __c. Every record has an 18-character Id whose first three characters identify the object.

    4. Security is layered

    Can the user log in? Can they see this object? This field? This specific record? Each question has its own mechanism. Most "I can't see it" tickets come from mixing these layers up.

    5. Clicks before code

    Salesforce's own guidance: use declarative tools (Flow, validation rules, formula fields) first, Apex when you need it. Code costs more to test, deploy and maintain, and must hit 75% test coverage to deploy.

    6. Three releases a year

    Spring, Summer and Winter releases land automatically. Sandboxes get them early (preview). Features get retired on a schedule — Workflow Rules and Process Builder are already out of support — so release notes matter.

    Orgs, editions and environments

    Productionthe real org

    Where your users and live data are. You can't write Apex directly here; you deploy into it.Edition (Professional, Enterprise, Unlimited) controls which features and limits you get. Most companies are on Enterprise or Unlimited.

    Sandboxescopies of production

    Developer and Developer Pro copy metadata only. Partial Copy adds a sample of data. Full copies everything, and refreshes less often (29 days).Refreshing a sandbox wipes it and recopies production.

    Scratch orgsdisposable, source-driven

    Short-lived (up to 30 days) orgs created from a config file by the sf CLI. Built from your source code, not from production.Requires a Dev Hub (enable it in production or a Developer Edition org).

    Developer Editionyour free playground

    A free, permanent, standalone org. Not connected to any company. Perfect for learning and Trailhead.

    Where things live in the UI

    Setup

    The gear icon, top right → Setup. Use the Quick Find box: type "Object Manager", "Users", "Flows", "Permission Sets". You'll live here.

    Object Manager

    Every object's fields, relationships, page layouts, record types, validation rules, triggers and buttons — one tab per object.

    App Launcher

    The waffle (9 dots) top left. Switches between Lightning apps (Sales, Service, your custom apps), which are just collections of tabs.

    Developer Console & VS Code

    Gear → Developer Console for quick queries and logs. Real development happens in VS Code with the Salesforce Extension Pack and the sf CLI.

    Relationship types

    TypeBehaviourUse when
    LookupLoose link. Child can exist without a parent; child has its own owner and sharing. Optional by default.Two things are related but independent (Case → Asset).
    Master-detailTight link. Detail can't exist without master; deleting master deletes details. Detail inherits owner and sharing. Enables roll-up summary fields on the master.The child is part of the parent (Invoice → Invoice Line).
    Many-to-manyA junction object with two master-detail fields.Students ↔ Courses via Enrollment__c.
    HierarchicalLookup from User to User only.Manager fields.
    External lookupLinks to an External Object (data living outside Salesforce via Salesforce Connect).Showing ERP orders without copying them in.

    Field types worth knowing

    Formula

    Read-only, calculated on read. Can reference parent fields (Account.Industry). Great for display logic; can't be used everywhere in filters if they're cross-object.

    Roll-up summary

    COUNT, SUM, MIN, MAX of child records — master-detail only. For lookups, use a Flow or Apex instead.

    Picklist

    Dropdown values. Use Global Value Sets to share values across objects. Restricted picklists reject API values not in the list.

    External ID

    Marks a field as the key from another system. Enables upsert by that key and is indexed.

    Record types vs page layouts: a record type changes which picklist values and business process a record uses (e.g., "Partner" vs "Customer" accounts). A page layout or Lightning record page (Dynamic Forms) changes what's shown. They're assigned per profile/record type combination.
    Chapter 04

    Security & sharing

    Access is decided in layers. A user must pass every layer to see a value: the org, the object, the field, then the record.

    flowchart TD
  A["Org access
    login, MFA, IP ranges, login hours"] --> B["Object access
    Create / Read / Edit / Delete"]
  B --> C["Field access
    Field-Level Security: read / edit"]
  C --> D["Record access"]
  D --> E["Org-Wide Defaults
    the baseline: Private / Public Read / Public Read-Write"]
  E --> F["Role hierarchy
    managers see subordinates' records"]
  F --> G["Sharing rules
    owner- or criteria-based, open access to groups"]
  G --> H["Manual sharing, teams, Apex managed sharing"]
    Profileexactly one per user

    The baseline: login hours, IP ranges, default apps, page layouts, and historically object/field permissions.Current best practice: keep profiles minimal (often "Minimum Access – Salesforce") and grant access with permission sets.

    Permission setmany per user

    Additive bundles of object, field, app, Apex class and system permissions. Permissions only ever add — nothing in Salesforce's permission model removes access.Permission Set Groups bundle sets into a persona ("Sales Rep"), and can mute individual permissions inside the group.

    Org-Wide Defaultsper object

    The most restrictive record access everyone starts from. Set the OWD as tight as the most restricted user needs, then open up.Separate internal and external (community/portal) defaults.

    Role hierarchyvertical sharing

    Users higher up see (and by default edit) records owned by people below them. Roles model data visibility, not the org chart.

    Sharing ruleshorizontal sharing

    Owner-based ("records owned by West team → share with East team") or criteria-based ("Accounts where Region = EMEA → share with EMEA group").

    Everything elseexceptions

    Manual shares, Account/Opportunity/Case teams, territory management, and Apex managed sharing (writes to __Share objects).Restriction rules go the other direction: they filter which records a user can see even if sharing grants them.

    Apex runs in system mode by default. It ignores object, field and record permissions unless you tell it otherwise. Declare classes with sharing to enforce record sharing, and use WITH USER_MODE in SOQL or insert as user for DML to enforce object and field permissions too.

    Debugging "I can't see it"

    1. Is the field on the page layout / Lightning page? (Not security, but it's the most common cause.)
    2. Does the user have Read on the object? Check their profile and permission sets (Setup → Users → user → View Summary).
    3. Field-Level Security: is the field visible for them?
    4. Record access: on the record, click Sharing → Sharing Hierarchy or run a UserRecordAccess query to see why they do or don't have access.
    5. Is a restriction rule or a scoping rule filtering it?
    Chapter 05

    Automation with clicks

    Flow is the automation tool. Workflow Rules and Process Builder reached end of support at the end of 2025 — if you find them in an org, they're migration candidates.

    Flow typeStarts whenTypical use
    Record-triggered (before save)A record is created/updated, before it's writtenFast field updates on the same record. No DML needed — just set the field. Very cheap.
    Record-triggered (after save)After the record is writtenCreate/update related records, send emails, call actions. Can add async paths and scheduled paths.
    Screen flowA user launches it (button, Lightning page, utility bar)Guided wizards, data entry, multi-step forms.
    Schedule-triggeredA time, recurringNightly clean-up, batch updates over a set of records.
    AutolaunchedCalled by Apex, another flow, REST API, or a buttonReusable logic (subflows).
    Platform event-triggeredA platform event message is publishedReacting to integration events.

    Other declarative tools

    Validation rules

    A formula that, when it returns true, blocks the save with an error message. AND(ISPICKVAL(StageName,"Closed Won"), ISBLANK(Amount))

    Approval processes

    Route a record for sign-off, lock it while pending, and run actions on approve/reject. Flow Approval Orchestration is the newer alternative for multi-step approvals.

    Assignment & escalation rules

    Route new Leads and Cases to the right queue or owner; escalate Cases that sit too long.

    Duplicate & matching rules

    Detect duplicate Leads/Contacts/Accounts on save and either warn or block.

    Flow best practices

    One trigger flow per object per context — or use Trigger Order

    Many flows on the same object fire in an unpredictable sequence unless you set the Trigger Order value. Keep the count low and organised.

    Never put Get/Create/Update elements inside a Loop

    Flows are bulkified across a batch of records, but DML or queries inside loops still multiply. Collect into a collection variable and do one Update after the loop.

    Use entry conditions

    "Only when a record is updated to meet the condition requirements" stops the flow from re-running on every edit.

    Add fault paths

    Connect a fault connector from any element that can fail, and log or surface the error. Unhandled faults email the admin and roll back the whole transaction.

    Before-save for same-record updates

    Up to ~10× faster than after-save, because it doesn't need another DML.

    Chapter 06

    Order of execution

    When a record is saved, Salesforce runs a fixed sequence. Knowing it answers "why did my value get overwritten?" (Simplified; highlighted steps are the ones you'll touch most.)

    1. Load the original record (or initialise a new one) and apply the new field values.
    2. System validation (from the UI only): required fields, field formats, max length.
    3. Before-save record-triggered flows
    4. Before triggers (Apex)
    5. System validation again, then custom validation rulesValidation runs after before-triggers, so a trigger can fix a value before it's validated.
    6. Duplicate rules
    7. Record saved to the database — not yet committed
    8. After triggers (Apex)
    9. Assignment rules, auto-response rules
    10. Legacy workflow rules (if any remain) — field updates here re-run before/after update triggers once more
    11. Escalation rules
    12. After-save record-triggered flows
    13. Entitlement rules
    14. Roll-up summary fields recalculated on the parent → the parent goes through its own save cycle
    15. Criteria-based sharing evaluated
    16. Commit — all DML in the transaction becomes permanent
    17. Post-commit: emails sent, async Apex (future/queueable) and "publish after commit" platform events run
    Everything up to the commit is one transaction. An unhandled exception anywhere — a trigger, a flow fault, a validation rule — rolls back every change. And all of it shares one set of governor limits.

    Chapter 07

    Apex

    Apex is a strongly-typed, Java-like language that runs on Salesforce's servers. It has database operations built in, and every line runs inside governor limits.

    Language crash course

    Triggers: the handler pattern

    Triggers fire on DML events for an object. Rule one: one trigger per object, containing no logic — it just delegates to a handler class. Rule two: always bulkify. A trigger receives up to 200 records at a time (data loads, API calls), so never run SOQL or DML inside a loop.

    Context variableWhat it holdsAvailable in
    Trigger.newList of new versions of the recordsinsert, update, undelete (editable only in before)
    Trigger.oldList of old versionsupdate, delete
    Trigger.newMap / oldMapMap of Id → recordnewMap: after insert, before/after update, after undelete. oldMap: update, delete
    Trigger.operationTypeEnum like BEFORE_INSERT, AFTER_UPDATEAll
    Trigger.isExecutingTrue when inside a trigger contextAll

    Asynchronous Apex

    TypeHowUse when
    Queueableimplements Queueable, System.enqueueJob(new MyJob())The default choice. Takes complex parameters, returns a job Id, can chain to another job, can make callouts with Database.AllowsCallouts.
    Future@future static method, primitive params onlySimple fire-and-forget, or callouts from a trigger. Largely superseded by Queueable.
    Batchimplements Database.Batchable<SObject>: start / execute / finishProcessing many records (up to 50 million) in chunks of 1–2,000, each chunk with fresh limits.
    Schedulableimplements Schedulable, System.schedule(name, cron, job)Running something on a timetable — usually kicks off a batch.

    Testing

    To deploy Apex to production, tests must cover at least 75% of your Apex code overall, every trigger needs some coverage, and all tests must pass. Tests run against an empty database (they can't see org data unless you use the discouraged SeeAllData=true) and roll back automatically.

    Write tests that assert behaviour, not tests that just touch lines. Cover the bulk case (200 records), a negative case, and a run-as-a-restricted-user case with System.runAs. Use HttpCalloutMock for callouts — real callouts aren't allowed in tests.
    Chapter 08

    SOQL & SOSL

    SOQL looks like SQL but isn't. There's no SELECT *, no arbitrary joins — you traverse relationships instead. SOSL is full-text search across many objects at once.

    SOQL vs SQL: the differences that bite

    No SELECT *

    List every field. FIELDS(ALL) exists but only with LIMIT 200; FIELDS(STANDARD) works anywhere.

    Relationships, not joins

    Child → parent with dot notation (Account.Name, up to 5 levels). Parent → child with a subquery using the child relationship name (Contacts, Line_Items__r).

    Querying a field you didn't select throws an error

    SObjectException: SObject row was retrieved via SOQL without querying the requested field. Add the field to the SELECT.

    Selective queries matter on big objects

    Filter on indexed fields (Id, Name, lookups, External IDs, CreatedDate, SystemModstamp) or the query can time out on large tables. Avoid leading-wildcard LIKE '%x' and != filters there.

    Use bind variables

    WHERE Id IN :ids in static SOQL is safe from injection. In dynamic SOQL use Database.queryWithBinds or String.escapeSingleQuotes.

    Chapter 10

    Lightning Web Components

    LWC is Salesforce's UI framework, built on web standards: custom elements, shadow DOM, ES modules. If you know modern JavaScript, you know most of it already.

    A component is a folder

    accountList/ containing accountList.js, accountList.html, optional .css, and accountList.js-meta.xml (where it can be placed).

    Decorators

    • @api — public property set by the parent (or the page, e.g. recordId)
    • @wire — reactive data from Apex or Lightning Data Service
    • @track — rarely needed now; fields are reactive by default

    Getting data

    • Lightning Data Service (lightning/uiRecordApi): no Apex, cached, respects security
    • Base components: lightning-record-form does a whole form
    • Apex: @AuraEnabled methods for anything custom

    Talking between components

    • Parent → child: @api properties
    • Child → parent: CustomEvent
    • Unrelated components: Lightning Message Service
    Aura and Visualforce are the older UI frameworks. You'll meet them in existing orgs and can embed LWCs inside Aura, but build new things in LWC.

    Data moves in two directions. Inbound: other systems call Salesforce APIs. Outbound: Salesforce calls out, or publishes events others subscribe to.

    ToolDirectionUse when
    REST APIInCRUD and queries on individual records. /services/data/vXX.X/sobjects/Account/
    Composite APIInSeveral REST calls in one round trip, optionally all-or-nothing.
    Bulk API 2.0InLoading or extracting thousands to millions of records asynchronously via CSV.
    GraphQL APIInFetch exactly the fields and related records a client needs in one query.
    Apex RESTInYour own endpoint: @RestResource(urlMapping='/orders/*') with custom logic.
    Apex calloutsOutHttpRequest to an external API. Use a Named Credential + External Credential so auth and the endpoint aren't hardcoded.
    Platform EventsBothEvent-driven, decoupled messaging. Publish from Apex/Flow/API; subscribe with triggers, flows, or the Pub/Sub API.
    Change Data CaptureOutStream every create/update/delete on chosen objects to external subscribers — keep a data warehouse in sync.
    Salesforce ConnectIn (virtual)Show external data as External Objects without copying it (OData, custom adapters).
    MuleSoftBothEnterprise integration platform when you have many systems and need an API layer.

    Authentication

    External systems authenticate with OAuth 2.0 through an app definition in Salesforce. New orgs use External Client Apps; older orgs are full of Connected Apps, which still work but are no longer the default for new apps. Common flows:

    • JWT Bearer — server-to-server with a certificate, no user interaction. The usual choice for back-end integrations.
    • Client Credentials — server-to-server with a client secret, running as a designated integration user.
    • Web Server (Authorization Code + PKCE) — a user logs in and approves access.

    Give every integration its own integration user (there's a free "Salesforce Integration" license for API-only users) with a narrow permission set.

    DevOps & the sf CLI

    Modern Salesforce development is source-driven: metadata lives in Git, you develop in a sandbox or scratch org, and you deploy with the sf CLI or a pipeline.

    flowchart LR

    validate & run tests" --> Q["QA / UAT sandbox"]
  Q -- "sf project deploy

    ApproachWhat it isWhen
    Change setsPoint-and-click bundles of metadata sent between connected orgs.Small admin teams with no Git. No version control, no rollback.

    sf CLI + CIDeploy source with sf project deploy start from GitHub Actions, Azure Pipelines, etc.Developer teams — the standard.
    Unlocked packagesVersioned, installable modules of metadata from your own code.Large orgs splitting metadata into modules with clear dependencies.
