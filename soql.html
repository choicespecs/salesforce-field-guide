SOQL & SOSL

SOQL (Salesforce Object Query Language) reads records from one object and its relationships. SOSL (Salesforce Object Search Language) runs full-text search across many objects at once. Both look a little like SQL, but neither supports arbitrary joins or SELECT *, and both are bound by governor limits.

SOQL or SOSL?

Use SOQL when…Use SOSL when…
You know which object (and field) holds the dataYou don't know which object or field holds the text
You need exact filters, relationships, aggregates, sortingYou need word or phrase matching across text, email, phone and name fields
Results must be complete and currentRelevance-ranked results are fine (the search index updates asynchronously, so very new records may not appear yet)
You might need up to 50,000 rows2,000 rows total is enough
Typical uses: triggers, batch jobs, services, related listsTypical uses: custom search bars, "find anything" lookups, duplicate hunting by name or phone

Most Apex uses SOQL. SOSL is the tool for search boxes: SOQL's LIKE '%term%' across several fields on several objects is slow and can't use indexes, while SOSL searches a purpose-built index.

Where you run queries

  • Apex: inline in square brackets, [SELECT … ], or dynamically with Database.query / Search.query.
  • Developer Console → Query Editor tab. Runs SOQL and SOSL; SOSL results show one tab per object. Tick "Use Tooling API" for metadata such as ApexClass. It also hosts the Query Plan tool (see below).
  • CLI: sf data query --query "SELECT Id, Name FROM Account LIMIT 5" (add --result-format csv or --bulk); sf data search --query "FIND {Acme}" for SOSL.
  • REST API: GET /services/data/v64.0/query?q=SELECT+Id+FROM+Account and /search?q=FIND+{Acme}.
  • VS Code's SOQL Builder, Workbench and other tools. For real development prefer an IDE (VS Code with the Salesforce extensions, or IntelliJ with Illuminated Cloud) over the Developer Console; the console is still handy for quick queries, the Query Plan tool and log timing.

Finding object and field API names

Queries use API names, which often differ from the labels users see. A field labelled "Account Name" on Contact is AccountId; a custom object labelled "Invoice Line" might be Invoice_Line__c.

  1. Setup → Object Manager → pick the object. The Details page shows the object's API name.
  2. Fields & Relationships lists each field's API name in the Field Name column, plus its data type and whether it's Indexed.
  3. For lookups and master-detail fields, open the field to see its Child Relationship Name (used in parent-to-child subqueries).
  4. Schema Builder (Setup → Schema Builder) draws objects as tables with lines for lookups and master-detail relationships. It's the quickest way to understand an unfamiliar org's data model.

The full grammar, in the order the clauses must appear:

  • Keywords are not case-sensitive (select id from account works). Upper-case keywords are just convention.
  • String values use single quotes. String comparisons with = and LIKE are case-insensitive.
  • There's no SELECT *. List the fields you need, or use FIELDS() sparingly (see below).
  • Id is always returned in Apex even if you don't select it, but select it explicitly so readers aren't surprised.
  • Accessing a field you didn't query on an sObject throws SObjectException: SObject row was retrieved via SOQL without querying the requested field.

Why filter at all

It's tempting to query everything and filter in Apex. It doesn't scale, for three reasons:

Row limits

A transaction can retrieve at most 50,000 rows across all its queries, not per query. Unfiltered queries on a growing object hit this quickly.

Selectivity

Once an object holds hundreds of thousands of rows, queries without a selective filter on an indexed field fail outright in triggers and can time out elsewhere.

Time

Queries are usually the slowest thing in a transaction, and turning rows into sObjects uses CPU time (10 s sync, 60 s async). Fewer rows means faster code.

Filtering with WHERE

Logical operators: AND, OR, NOT

  • AND: every condition must be true. Chain as many as you need; each one narrows the result.
  • OR: at least one condition must be true.
  • NOT: negates the condition that follows. Rare, but useful with groups.
  • Use parentheses whenever you mix AND and OR. SOQL rejects ambiguous mixes like A AND B OR C without them.

Comparison operators

OperatorNotes
= != < <= > >== null and != null work (there's no IS NULL). <> also means not-equal.
LIKEText fields only; % = any number of characters, _ = exactly one. Case-insensitive. Escape a literal with backslash: '50\%'.
IN, NOT INLiteral list, Apex bind variable (List or Set), or subquery (semi-join / anti-join)
INCLUDES, EXCLUDESMulti-select picklists only
DISTANCE(…) < nGeolocation and address fields: DISTANCE(BillingAddress, GEOLOCATION(37.77,-122.41), 'mi') < 20

LIKE patterns

A leading % forces a scan of every row. On large objects, use SOSL for "contains" searches instead.

IN and NOT IN

IN is the operator you'll use most in Apex, because you usually have a set of Ids or values to look up in bulk (WHERE Id IN :accountIds). See bind variables.

Multi-select picklists

A multi-select picklist is stored as one string with values separated by semicolons (AAA;BBB). Don't use LIKE on it; use INCLUDES and EXCLUDES:

Fields you can't filter on

  • Long text area and rich text area fields can't appear in WHERE, ORDER BY or GROUP BY. Use SOSL to search their contents.
  • Encrypted fields (Classic encryption, and Shield probabilistic encryption) can't be filtered or sorted. Shield deterministic encryption allows exact-match filters.
  • Multi-select picklists only support =, !=, INCLUDES and EXCLUDES, and can't be sorted or grouped.
  • Most formula fields can be filtered but can't use an index unless Support adds one (deterministic formulas only).

To check a field in Apex, use its describe: DescribeFieldResult.isFilterable(), isSortable(), isGroupable().

Sorting with ORDER BY

  • ASC is the default, so you only ever need to write DESC.
  • Nulls sort first by default. Add NULLS LAST to push empty values to the end.
  • Without ORDER BY, row order is not guaranteed, and can change between runs. Always sort when order matters, especially with LIMIT or OFFSET.
  • Sort in the query, not in Apex: it's cheaper, and a component can display the result directly.
  • You can sort by up to 32 fields, but not by long text, rich text, multi-select picklist or encrypted fields.

LIMIT and OFFSET

  • LIMIT caps the rows a query returns. It doesn't lift the transaction-wide 50,000-row limit, but it stops one query from eating all of it.
  • OFFSET skips rows, which makes simple pagination for a UI: page n is LIMIT size OFFSET (n-1)*size.
  • OFFSET can be at most 2,000, can't be used in subqueries (with a few exceptions) and gets slower as it grows.

Relationship queries

Objects are linked by lookup and master-detail fields. SOQL can follow those links in both directions. It's less flexible than SQL joins (you can only follow relationships that exist as fields), but it covers most needs.

Child to parent (dot notation)

From the child, follow the lookup with a dot. For a standard lookup, drop the Id suffix (AccountId → Account). For a custom lookup, change __c to __r (Invoice__c → Invoice__r).

Up to 5 levels up (A.B.C.D.E.Field), and up to 55 child-to-parent relationships in one query. If the lookup is empty, the parent fields come back as null rather than an error, but in Apex c.Account.Name throws a null pointer exception when c.Account is null. Use c.Account?.Name.

Parent to children (subquery)

From the parent, put a subquery in the SELECT list. Its FROM uses the child relationship name from the lookup field's definition, not the child object name. It's usually plural: Contacts, Opportunities, Cases, and custom ones end in __r (Invoices__r). In Object Manager, standard lookups show it near the top of the field page; custom lookups show it further down.

Each subquery can have its own WHERE, ORDER BY and LIMIT. Up to 20 subqueries per query; nesting up to 5 levels deep in recent API versions. In the Query Editor, child rows appear as a nested JSON-like cell.

Large child sets: if a parent might have more than about 200 children, iterate the subquery results inside a SOQL for-loop (for (Account a : [SELECT …, (SELECT … ) FROM Account])), otherwise you can hit QueryException: Aggregate query has too many rows for direct assignment.

Semi-joins and anti-joins

Filter one object by whether related rows exist in another with IN / NOT IN and a subquery that selects a single Id or lookup field.

Rules: at most two semi/anti-join subqueries per query, no nesting them, no OR around them, and the inner query can't use ORDER BY or LIMIT.

Aggregates, GROUP BY and HAVING

Aggregate functions

FunctionReturns
COUNT()Number of rows (no field, returns an Integer in Apex)
COUNT(field)Number of rows where the field isn't null
COUNT_DISTINCT(field)Number of distinct non-null values
SUM(field), AVG(field)Total and average of a number or currency field
MIN(field), MAX(field)Smallest and largest value (numbers, dates, and also text and picklists)

GROUP BY

GROUP BY splits the rows into groups and runs the aggregates once per group, like the groupings in a summary report. Every selected field that isn't inside an aggregate must be in the GROUP BY.

HAVING

WHERE filters rows before grouping and can't use aggregates. HAVING filters groups after aggregation.

Aggregates in Apex

Aggregate queries still count every row they scan toward the 50,000-row limit, and return at most 2,000 groups. For larger summaries, use batch Apex or a report.

Security clauses

Apex runs in system mode by default: it ignores the running user's object and field permissions. SOQL has clauses to bring them back.

Locking and recently viewed

A query that uses FOR UPDATE can't use ORDER BY. Lock as few rows as you can, for as short a time as you can.

Selecting all fields with FIELDS()

FIELDS() is SOQL's closest thing to SELECT *.

  • FIELDS(ALL) and FIELDS(CUSTOM) need LIMIT 200 or less. FIELDS(STANDARD) has no such restriction.
  • Use it for exploring data, not in production code: it fetches data you don't need, slows queries, and a new field quietly changes what your code retrieves.

Other clauses and functions

SOQL in Apex

In Apex, wrap a query in square brackets and assign it. Salesforce generates a typed class for every object (Account, Invoice__c), so there's no connection or mapping code to write.

Run it from Debug → Open Execute Anonymous Window in the Developer Console (or sf apex run) with System.debug(AccountQueries.withRevenue()); and check the debug log.

Bind variables

Put a colon before an Apex variable or expression to use it in the query. Binds are type-safe and immune to SOQL injection.

Single records, loops and large results

SOQL inside a loop is the classic way to hit Too many SOQL queries: 101. Each transaction gets 100 queries (200 async). Query once with IN :ids and use a map. See Governor limits.

Dynamic SOQL

Dynamic SOQL builds the query as a string at runtime, for example from custom metadata, a field set, or user-chosen filters, then runs it with the Database class.

Trade-off: fields and objects referenced only inside query strings are invisible to Salesforce's dependency tracking. "Where is this used?" won't list them, and the platform won't stop an admin deleting a field your dynamic query needs. The query then fails at runtime. Prefer static SOQL when the shape is fixed.

SOQL and SOSL injection

Injection happens when user input is concatenated into a query string, letting a crafted value change the query's logic, for example to read records or fields the user shouldn't see.

  • Bind variables are always safe; escaping is for values you concatenate.
  • The same applies to SOSL: bind the search term, or escape it before building a Search.query string.
  • Treat anything from an LWC, Visualforce page, URL parameter or API call as untrusted. Injection is one of the most common AppExchange security review failures.

Measuring query cost

The database work for a query isn't counted as Apex CPU time, but turning the returned rows into sObjects is, and for large result sets that's significant. Measure rather than guess.

For a visual breakdown, open the log in the Developer Console and choose Debug → View Log Panels → Execution Overview (or Switch Perspective → Analysis). The timeline shows each SOQL statement, how long it took, and the line it ran from. Limits.getQueries() and Limits.getQueryRows() show how much of each limit you've used.

The Query Plan tool

On large objects, a query must be selective: its filters must narrow the rows enough for the optimiser to use an index. When an object grows past a few hundred thousand rows, non-selective queries that used to work start failing (System.QueryException: Non-selective query against large object type in triggers) or timing out. The Query Plan tool shows how Salesforce would run a query before that happens.

  1. In the Developer Console, Help → Preferences → Enable Query Plan. A Query Plan button appears in the Query Editor.
  2. Type the query (it isn't run) and click Query Plan.
  3. Read the top row: that's the plan the optimiser will choose. Its Cost should be below 1.
  4. If it's a TableScan or cost is 1 or more, add or change a filter on an indexed field and re-check.

Big objects and very large queries

Big objects (__b) store billions of rows for archives and history. SOQL against them is heavily restricted, because they're queried only through their defined index.

  • Filter on the index fields in the order they're defined, starting from the first, with no gaps.
  • Use = on every index field except the last one you filter on, which can use a range (<, >, <=, >=) or IN. Only one IN per query.
  • Not supported: !=, LIKE, NOT IN, INCLUDES, EXCLUDES, aggregate functions, GROUP BY, HAVING, OFFSET.
  • Don't select Id: big object rows return an empty placeholder Id.

Async SOQL, which once ran long queries over big objects via a REST API and wrote results to another object, has been retired. For queries beyond normal limits, use:

  • Batch Apex with Database.getQueryLocator: iterates up to 50 million rows in chunks.
  • Bulk API 2.0 query jobs (sf data query --bulk) for large extracts.
  • Apex cursors (Database.getCursor) to page through up to 50 million rows across queueable jobs.

SOSL basics

A SOSL query has three main parts: what to look for, where to look, and what to return.

Read it as: "find Taco in any name field, and give me back matching accounts with their Id and Name, and matching contacts with their Id, first and last name." The Query Editor shows one results tab per object. Matching works on whole words and is more forgiving than =: {Taco} finds "Taco Bell" and "Extra Taco", and a contact whose last name is Taco.

The search term (FIND)

SyntaxMeaningExample
*Any number of characters, in the middle or at the end of a word (SOSL's version of %){Tac*} → Taco, Tacos, Tackle
?Exactly one character (SOSL's version of _){T?co} → Taco, Tico
"…"Exact phrase, words in that order{"Taco Bell"}
AND, ORBoth terms / either term{Taco OR Burrito}
AND NOTFirst term but not the second{Tacos AND NOT Batchable}
( )Grouping{(Taco OR Tacos) AND Batchable}
  • A plain single term is matched loosely: the engine uses word stemming, so {Taco} can also match "Tacos". Wildcards, quotes and boolean operators make matching stricter: once you write {Taco OR Batch}, each term must match a whole word, so "Tacos" may no longer match. If results shrink unexpectedly, list the variants ({Taco OR Tacos}) or add *.
  • Terms need at least two characters (wildcard searches more). The search is case-insensitive.
  • Escape reserved characters with a backslash: ? & | ! { } [ ] ( ) ^ ~ * : \ " ' + -.
  • In Apex inline SOSL, the term is in single quotes instead of braces: FIND 'Taco*'.

Search groups (IN … FIELDS)

Unlike SOQL, you don't name individual fields to search. You pick one predefined group:

GroupSearches
ALL FIELDSEvery searchable text field (the default). Includes long text areas, which SOQL can't filter.
NAME FIELDSName-type fields on each object (Account Name, Contact first/last name, Case Subject, etc.)
EMAIL FIELDSEmail fields only
PHONE FIELDSPhone fields only, with phone-number normalisation
SIDEBAR FIELDSThe fields the classic sidebar search used: a narrower, faster set of key fields per object

RETURNING

Each object in RETURNING takes what is essentially a mini SOQL query in parentheses, without SELECT or FROM:

  • Order inside the parentheses: fields, then WHERE, then ORDER BY, then LIMIT, then OFFSET.
  • OFFSET is allowed only when RETURNING lists a single object.
  • Without a field list, only the record Ids come back.
  • USING ListView=… restricts an object's results to records in that list view.
  • toLabel() returns translated picklist values when Translation Workbench is on.
  • The overall LIMIT applies across all objects; the per-object limits apply within each one.

SOSL in Apex

Because SOSL can return several object types at once, the result is a list of lists: one inner list per object, in the same order as the RETURNING clause.

  • Inline: FIND 'Taco*' with a literal, or FIND :term with a bind variable (wildcards can be part of the bound string).
  • An inner list is empty, not null, when an object has no matches.
  • In tests, SOSL returns nothing unless you call Test.setFixedSearchResults(ids) first. See Testing Apex.
