Order of execution

When a record is saved, Salesforce runs a fixed sequence of steps. Knowing it explains "why did my value get overwritten?" and "why did this run twice?"

The sequence

Simplified from the official list; highlighted steps are the ones you'll work with most.

  1. Load the original record from the database (or initialise a new one) and apply the new field values.From the UI, the browser has already checked dependent picklists and field lengths.
  2. System validation (UI saves): required fields on the layout, field formats, max lengths. API and Apex saves only check things like foreign keys here.
  3. Before-save record-triggered flows (Fast Field Updates)
  4. Before triggers (Apex)
  5. System validation again (now for all saves: required fields at field level, formats), then custom validation rules.Because validation runs after before-triggers, a trigger can fix a value before it's validated.
  6. Duplicate rules. A blocking rule stops the save here.
  7. Record is saved to the database but not committed. The ID now exists.
  8. After triggers (Apex)
  9. Assignment rules (leads, cases)
  10. Auto-response rules
  11. Workflow rules (legacy). If a workflow field update fires, the record is updated again and before and after update triggers run one more time (custom validation rules do not).
  12. Escalation rules
  13. Processes (legacy Process Builder) and flows they launch
  14. After-save record-triggered flows
  15. Entitlement rules
  16. Roll-up summary fields on the parent are recalculated → the parent goes through its own save procedure. Same for grandparents.
  17. Criteria-based sharing evaluated
  18. Commit: all DML in the transaction becomes permanent.
  19. Post-commit: emails are sent, async Apex (queueable, future) starts, platform events published "after commit" are delivered, asynchronous flow paths run.

One transaction, one set of limits

Everything from step 1 to the commit is one transaction:

  • An unhandled exception anywhere — a trigger, a flow fault, a validation rule failing on a child record you updated — rolls back every change in the transaction.
  • All triggers, flows and roll-ups share one set of governor limits. A flow that does 30 queries and a trigger that does 80 together exceed the 100-query limit.
  • DML inside a trigger starts the whole sequence again for the other object, nested inside the same transaction.
sequenceDiagram
  participant U as User saves Opportunity
  participant O as Opportunity automation
  participant A as Account automation
  U->>O: before flows, before triggers, validation
  O->>O: save (uncommitted)
  O->>O: after triggers → update Account
  O->>A: Account: before → validation → save → after
  A-->>O: back to Opportunity
  O->>O: after-save flows
  O->>A: roll-up recalculates → Account saves again
  O->>U: commit (or roll back everything)

Bulk saves

When many records are saved together (API, Data Loader, a flow updating a collection), Salesforce processes them in chunks of 200. Each step runs once per chunk with all 200 records: the before trigger sees Trigger.new with 200 records, then validation runs for all 200, and so on. That's why bulkified code matters: one query per chunk, not one per record.

With allOrNone = false (partial success), records that fail validation are removed and the remaining ones are re-run through the triggers, so triggers can execute more than once for the same records (up to three attempts).

Explaining common surprises

SymptomExplanation
A value set in a before-save flow is overwrittenA before trigger runs after before-save flows and changed it.
A trigger fires twice for one saveA legacy workflow field update re-runs update triggers; or a roll-up on a parent updates the parent, whose trigger updates the child again. Add recursion control (Triggers).
A validation rule didn't block a value set by automationValues set by legacy workflow field updates re-run triggers but not custom validation rules. Values set in a before trigger are validated, because validation runs after it.
A callout fails with "uncommitted work pending"DML already happened in this transaction. Move the callout to a queueable or an async flow path (post-commit).
An email was sent even though the save failedIt wasn't: emails go out post-commit. If you saw one, it came from a separate, successful transaction (e.g. async path or a retried save).
Platform event received for a record that doesn't existThe event was published "immediately" and the transaction later rolled back. Use "publish after commit" for events about saved data.
Changing a child record changes the parent's LastModifiedDateA roll-up summary on the parent recalculated and saved the parent.

What doesn't follow this sequence

  • Some operations skip triggers: cascade-deleting master-detail children, mass address updates, renaming picklist values, and a few others don't fire triggers on the affected records.
  • Lead conversion fires triggers on the lead and on the created account, contact and opportunity — but not validation rules on the lead unless enabled in Lead Settings.
  • Merge fires delete triggers on the losing records and update triggers on the winner.
  • Undelete fires after undelete triggers only.
