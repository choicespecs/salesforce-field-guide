Admin essentials

The everyday tasks behind a well-run org: managing users, shaping the UI, moving data in and out, and keeping track of what changed.

Users

Creating a user

  1. Setup → Users → New User.
  2. Username must be unique across all Salesforce orgs and look like an email (it doesn't have to be a real mailbox): jane.doe@acme.com.uat is fine for a sandbox.
  3. Choose the user licence and a profile (ideally a minimal one).
  4. Set the role for record visibility.
  5. Save, then assign permission set groups / permission sets and any permission set licences.

Bulk-create users with Data Loader (insert on User) or the sf CLI: sf org create user --definition-file config/user-def.json for scratch orgs.

Apps, tabs and pages

Lightning app

A named set of tabs (navigation items) with branding and utility bar. App Manager → New Lightning App. Assign to profiles.

Tab

Every custom object needs a tab to appear in navigation. Tab visibility (Default On / Default Off / Hidden) is set in profiles and permission sets.

Lightning App Builder

Build record pages, app pages and home pages from components. Activate a record page per org default, app, record type and profile.

Utility bar

The footer of an app: notes, recent items, a softphone, a screen flow, a custom LWC.

Path

A stage-by-stage guide on a record page with key fields and guidance for each picklist value.

Quick actions

Buttons that create related records, update fields, log calls or launch flows/LWCs. Object-specific or global.

List views

  • Filter by owner (My, All, My team's, a queue), field criteria with filter logic (1 AND (2 OR 3)).
  • Share with all users, groups or roles. Pin a default list view.
  • Display as table, Kanban (drag records between picklist columns), or split view.
  • Inline-edit fields directly in the list view, and select several rows to edit a field on all of them at once.

A safe data load, step by step

  1. Export first: back up the records you'll touch (Data Loader export with IDs).
  2. Prepare the file: one column per field, API names as headers, dates as YYYY-MM-DD, datetimes in ISO 8601 UTC, checkboxes as true/false, picklists using API values.
  3. Use External IDs to relate records without looking up Salesforce IDs: set Account.ERP_Id__c on accounts, then load contacts with a column mapped to Account:ERP_Id__c.
  4. Think about automation: flows, triggers, validation rules and emails fire on loads. Use a bypass custom permission for the loading user, or temporarily deactivate rules.
  5. Load a small sample (10 rows) and check the results, success file and error file.
  6. Tune batch size: lower it (e.g. 50) when triggers hit limits or you see UNABLE_TO_LOCK_ROW.
  7. Verify with a report or a query count.

Duplicate management

A matching rule defines how to compare records (exact or fuzzy on name, email, phone, address). A duplicate rule says what to do when a match is found: allow with alert, allow and report, or block, and for which users. Standard rules for accounts, contacts and leads exist out of the box. Duplicate rules run on UI and API saves; Apex and Data Loader saves can be configured to respect them (Database.DMLOptions.DuplicateRuleHeader).

Queues and assignment

  • A queue can own Leads, Cases, and custom objects (and some others). Members work records from the queue's list view, taking ownership.
  • Lead and case assignment rules route new records to users or queues by criteria. Only one rule per object is active; entries are evaluated in order.
  • Omni-Channel pushes work to available agents by capacity and skills (see Service).

Email

  • Deliverability (Setup → Deliverability): sandboxes default to "System email only", so emails from flows don't go out until you change it to "All email".
  • Organization-wide email addresses: shared "from" addresses like support@acme.com, which must be verified.
  • Email templates: Lightning email templates (with merge fields like {{{Recipient.FirstName}}}) or Classic (Text, HTML, Visualforce).
  • Email-to-Case and Enhanced Email store emails as EmailMessage records.
  • Set up DKIM and SPF so mail from Salesforce isn't treated as spam.

Debug logs

  1. Setup → Debug Logs → New trace flag for the user (or Automated Process, or a platform integration user).
  2. Pick a debug level: for Apex debugging set Apex Code = FINEST, Database = INFO, Workflow = INFO (Flow also logs under Workflow).
  3. Reproduce the issue, then open the log. Search for FATAL_ERROR, EXCEPTION_THROWN, VALIDATION_FAIL, FLOW_ELEMENT_ERROR, USER_DEBUG.
  4. The LIMIT_USAGE_FOR_NS block at the end shows how close the transaction came to each limit.

Logs over 20 MB are truncated. Lower the noisy categories (e.g. System, Visualforce) to NONE.

Change management for admins

  • Build in a sandbox, never directly in production (except for low-risk items like list views and reports).
  • Move changes with change sets (Setup → Outbound Change Sets → upload to production → deploy from Inbound Change Sets) or DevOps Center, which tracks work items and commits to Git for you.
  • Write a short description on every field, flow and validation rule. The next admin will thank you.
  • Check Where is this used? before deleting fields. Deleted fields sit in the Recycle Bin for 15 days, then are gone along with their data.
