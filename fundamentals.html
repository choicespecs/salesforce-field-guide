Platform fundamentals

The handful of ideas that explain most of Salesforce's behaviour, including the parts that surprise developers coming from ordinary web stacks.

Multi-tenancy

Salesforce runs thousands of customers on shared infrastructure. Each customer's slice is an org (organisation): its own data, configuration, users and code, isolated logically rather than physically. Orgs live on instances (server pods with names like NA224 or EU46) in Salesforce's data centres or on Hyperforce, its public-cloud infrastructure.

Because tenants share CPU, memory and database capacity, the platform enforces governor limits: hard caps per transaction (100 SOQL queries, 150 DML statements, 10 seconds of CPU…) and per org per day (API calls, async jobs, emails). Limits are the single biggest difference between Salesforce development and general web development. See Governor limits.

Consequence: code that works for one record can fail for 200. Everything on the platform, including Flow, must be written for batches of records.

Everything is metadata

An object, a field, a page layout, a flow, an Apex class, a permission set and a report are all metadata: XML descriptions the platform reads at runtime. Creating a custom field in Setup doesn't run a database migration you control; it writes metadata, and the platform adapts.

  • Metadata can be retrieved to files, stored in Git and deployed to another org — that's how changes move from sandbox to production (DevOps).
  • Data (records) and metadata (configuration) move separately. Deploying a picklist doesn't move the records that use it.
  • Some settings are data-like but deployable: Custom Metadata Types (__mdt) let you ship configuration rows with your code.

That file is exactly what Setup creates when you add a Currency field called Amount. Clicks and code are two editors for the same metadata.

Separately from edition, each user has a user licence (Salesforce, Salesforce Platform, Salesforce Integration, Customer Community, Partner Community…) that sets which objects and features they can ever use, and optional permission set licences for add-on features. A Platform licence user, for example, cannot access Opportunities or Cases regardless of permissions.

Sandboxes are copies of production made at refresh time; refreshing wipes the sandbox. Users are copied too, with .sandboxname appended to usernames and email addresses scrambled with .invalid so you don't email real customers. Log in to sandboxes at test.salesforce.com or via the My Domain URL.

Post-refresh tasks are common: reset integration endpoints, fix user emails, seed test data. Automate them with an Apex class implementing SandboxPostCopy, which runs automatically after a sandbox is created or refreshed.

Releases and API versions

Salesforce ships three major releases a year — Spring (Feb), Summer (Jun) and Winter (Oct, named for the following year). Sandboxes on preview instances get each release about a month early. Each release adds an API version (Winter '26 was 65.0; each release adds 1.0).

  • Every Apex class, trigger, LWC and flow stores the API version it was saved with. Behaviour is versioned: old code keeps old behaviour until you bump its version.
  • API clients choose a version in the URL: /services/data/v64.0/.
  • Release updates (Setup → Release Updates) are behaviour changes with an enforcement date. Test and enable them in a sandbox before they're forced on.
  • Features are retired on published schedules. Workflow Rules and Process Builder reached end of support on 31 December 2025; existing ones still run but get no fixes.

Lightning Experience vs Classic

Lightning Experience is the current UI: component-based pages built in Lightning App Builder, LWC, Dynamic Forms. Salesforce Classic is the pre-2016 UI; it still exists and some old orgs and Visualforce pages depend on it, but new features are Lightning-only. When documentation shows two sets of instructions, use the Lightning ones.

Storage

Orgs have two storage pools. Data storage counts records (most records count as 2 KB regardless of size). File storage counts files, attachments and documents. Check usage in Setup → Storage Usage. Running out blocks inserts, so archive old records and keep large binaries out of Salesforce when you can.
