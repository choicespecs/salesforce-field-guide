Data model

Objects are tables, fields are columns, records are rows. The differences from a relational database are in the relationship types, the built-in fields every object gets, and how the UI is generated from the schema.

Field options worth knowing

  • External ID: marks a field as another system's key. It's indexed and enables upsert by that key from Apex, the API, Data Loader and Flow.
  • Unique: enforces uniqueness (optionally case-sensitive). Gives an index too.
  • Required: at the field level it's enforced everywhere, including the API. Requiring it on a page layout only affects that layout in the UI.
  • Default value: a formula evaluated when a new record is created in the UI or API (if the field isn't set).
  • Field history tracking: up to 20 fields per object; history is queryable in AccountHistory, Invoice__History etc.
  • Global value sets: one picklist value list shared by many fields.
  • Dependent picklists: values in one picklist controlled by another picklist or checkbox.

Many-to-many with a junction object

Model "a Course has many Students and a Student takes many Courses" with an object in the middle that has two master-detail fields.

erDiagram
  Course__c ||--o{ Enrollment__c : "master"
  Student__c ||--o{ Enrollment__c : "master"
  Enrollment__c {
    string Status__c
    date Enrolled_On__c
    number Grade__c
  }

The first master-detail field you create is the primary master: it controls the junction record's look and feel and, together with the second, its sharing (users need access to both masters). Roll-ups work on both parents.

Special relationship types

  • Self relationship: a lookup to the same object, e.g. Account.ParentId.
  • Hierarchical: a lookup from User to User (ManagerId).
  • Polymorphic: one field can point to several object types (WhoId, WhatId, OwnerId which can be a User or a Queue). Query with TYPEOF (see SOQL).
  • External lookup / indirect lookup: links involving External Objects (__x) from Salesforce Connect.

Relationship names in code

Each relationship has two names: the field (holds the ID) and the relationship name (traverses to the related record).

Record types

A record type lets one object support different processes. Each record type has its own picklist values, page layout assignment (per profile) and, for Leads, Opportunities, Cases and Solutions, its own business process (which stages or statuses are available).

Example: Opportunity record types New Business and Renewal, where Renewal has fewer stages and a different layout. Users need the record type assigned (via profile or permission set) to create records of that type.

Don't use record types just to change the layout. If only the visible fields differ, use Dynamic Forms visibility rules on a single Lightning record page. Record types are for different processes.

Page layouts, Lightning pages and Dynamic Forms

Page layout

Which fields, related lists, buttons and quick actions appear, and which fields are read-only or required in the UI. Assigned by profile × record type.

Lightning record page

The page's overall structure built in Lightning App Builder: tabs, components, related lists, custom LWCs. Assigned by app, record type and profile ("activation").

Dynamic Forms

Place individual fields and field sections directly on the Lightning page, with visibility rules (e.g. show Loss Reason only when Stage = Closed Lost). Replaces most uses of multiple page layouts.

Dynamic Actions

Show buttons/actions conditionally (e.g. show "Escalate" only for high-priority cases).

Compact layout

The fields shown in the record highlights panel at the top and on mobile.

Search layout

Columns shown in search results and lookup dialogs.
