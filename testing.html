Testing Apex

Tests are required to deploy Apex to production, but their real job is to prove behaviour and catch regressions. Good tests are bulk, assert outcomes, and run as realistic users.

The rules

  • At least 75% of Apex lines across the org must be covered, every trigger must have some coverage, and all tests must pass to deploy to production.
  • Tests run against an empty database: they can't see org data (except setup objects like Users, Profiles, RecordTypes) unless annotated @IsTest(SeeAllData=true) — avoid it.
  • All data created in a test is rolled back at the end. No emails are actually sent; callouts must be mocked.
  • Test classes and methods are annotated @IsTest and don't count toward the org's Apex size limit.

Anatomy of a test class

Assertions

MethodChecks
Assert.areEqual(expected, actual, msg)Equality
Assert.areNotEqual(a, b, msg)Inequality
Assert.isTrue(cond, msg) / isFalseBooleans
Assert.isNull(v, msg) / isNotNullNull checks
Assert.isInstanceOfType(obj, Type, msg)Type
Assert.fail(msg)Fails immediately (e.g. after code that should have thrown)

The older System.assertEquals family still works. Always pass a message: it's what you'll read when a deployment fails at 11pm.

Test data factory

Keep required fields and validation-rule-friendly values in one place, so a new validation rule means one fix, not fifty.

Running as another user

System.runAs enforces record sharing and lets you test as a specific user, but doesn't enforce object/field permissions on its own — code using WITH USER_MODE or as user does. It also starts a new context, so you can insert setup objects (User, PermissionSetAssignment) and regular records in the same test without MIXED_DML_OPERATION.

Testing async Apex

Async jobs enqueued between Test.startTest() and Test.stopTest() run synchronously at stopTest().

Mocking HTTP callouts

For several endpoints in one test, write a mock that switches on req.getEndpoint(), or use MultiStaticResourceCalloutMock with JSON files stored as static resources.

Mocking dependencies with the Stub API

Frameworks like ApexMocks (part of fflib) build on the Stub API with Mockito-style syntax.

Running tests

In the Developer Console: Test → New Run; coverage shows per class (blue = covered, red = not). In VS Code, click "Run Test" above a method.
