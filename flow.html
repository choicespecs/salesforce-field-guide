Flow

Flow is Salesforce's declarative automation tool. It replaces Workflow Rules and Process Builder, and handles most automation that doesn't need code.

Resources

Variable

Text, Number, Currency, Boolean, Date, Date/Time, Record (one sObject), Apex-defined type; single or collection. Tick Available for input/output to pass values in and out.

Constant

A fixed value.

Formula

Calculated on use, with the formula language: {!$Record.Amount} * 0.1, TODAY() + 7.

Text template

Multi-line text with merge fields, plain or rich text — email bodies.

Choice / record choice set / collection choice set

Options for screen picklists and radio buttons.

Global variables

Record-triggered flows in detail

$Record is the triggering record with its new values. In update-triggered flows, $Record__Prior holds the values before the change. Compare them to act only on a real change:

Parent fields are available without a Get Records: {!$Record.Account.Owner.Email}.

Entry conditions and "when to run"

  • Every time a record is updated and meets the condition requirements: runs on every save while the condition is true.
  • Only when a record is updated to meet the condition requirements: runs once when the record goes from not-matching to matching. Usually what you want, and the only option that allows scheduled paths.
  • Use entry conditions instead of a first Decision element: flows that don't match never start, which saves CPU.

Paths

Run Immediately

Synchronous, inside the triggering transaction.

Run Asynchronously

After the transaction commits, in a separate transaction with its own limits. Use for callouts and slow work.

Scheduled paths

Run at a time relative to a date field or the trigger time: "3 days before Contract End Date", "1 hour after creation". Re-evaluated if the record changes. Monitor in Setup → Time-Based Workflow / Scheduled Jobs.

Trigger order

With several record-triggered flows on the same object and timing, set Trigger Order (1–2000) on each so they run in a known sequence. Flows without one run after those with one, in an order you can't rely on. Many teams keep one before-save and one after-save flow per object, with decisions inside, or use Flow Trigger Explorer to see them all.

Fault handling

Any element that touches the database or calls an action can fail. Without a fault path, the whole transaction rolls back, the user sees "An unhandled fault has occurred", and the admin (or the flow's "last modified by" user) gets an email.

  • Drag a Fault connector from the element to a handler.
  • Log {!$Flow.FaultMessage} to a custom Flow_Error__c object or a platform event (platform events published "immediately" survive the rollback).
  • In screen flows, show a friendly screen; in record-triggered flows, use Custom Error to show a clean message.
  • Set Process Automation Settings → Send Process or Flow Error Email to a monitored mailbox.

Calling Apex from Flow

When Flow can't do something (complex parsing, a callout with logic, heavy calculations), expose Apex as an invocable action. Invocable methods are bulkified: Flow passes a list of requests, one per flow interview in the batch.

Worked examples

1. Default a field before save

Goal: new opportunities get a Close Date 30 days out if blank, and a Next Step for the stage.

  1. Record-triggered, object Opportunity, A record is created, optimise for Fast Field Updates.
  2. Decision: {!$Record.CloseDate} Is Null = True.
  3. Assignment: {!$Record.CloseDate} Equals formula TODAY() + 30.
  4. No Update element is needed: before-save flows write directly to $Record.

2. Create a follow-up task when a deal is won

  1. Record-triggered, Opportunity, created or updated, Actions and Related Records.
  2. Entry condition: StageName Equals Closed Won; run only when updated to meet the condition.
  3. Create Records: Task with WhatId = {!$Record.Id}, OwnerId = {!$Record.OwnerId}, Subject = "Kick-off call", ActivityDate = {!$Flow.CurrentDate} + 2 (formula).
  4. Fault path → Create Records on Flow_Error__c with {!$Flow.FaultMessage}.

3. Update all contacts when an account's address changes

  1. Record-triggered on Account, updated, entry condition ISCHANGED({!$Record.BillingStreet}) (use a formula entry condition).
  2. Get Records: Contacts where AccountId = {!$Record.Id}, all records.
  3. Loop over contacts → Assignment sets MailingStreet etc. on the loop variable → Assignment Add loop variable to contactsToUpdate collection.
  4. After the loop: one Update Records with contactsToUpdate.

Even simpler: an Update Records element can update "records that meet conditions" (AccountId = {!$Record.Id}) and set fields directly, with no loop.

4. Renewal reminder 60 days before contract end

  1. Record-triggered on Contract, created or updated, entry condition Status = Activated, run only when updated to meet the condition.
  2. Scheduled path: 60 days before EndDate.
  3. On that path: Create a renewal Opportunity and send an email alert to the account owner.

5. A screen flow to log a customer escalation

  1. Screen flow with input variable recordId (Text, available for input) — Lightning pages pass the current record ID automatically.
  2. Get Records: the Case by recordId.
  3. Screen: picklist for Severity, long text for Summary, a checkbox "Notify account owner"; use conditional visibility to show a manager lookup only for Severity = Critical.
  4. Update Records: set Escalated__c = true, Priority from Severity.
  5. Decision on the checkbox → Send Email action.
  6. Add the flow to the Case page as a quick action (Object Manager → Case → Buttons, Links and Actions → New Action → Flow).

Testing and debugging

  • Debug button in Flow Builder: run with chosen inputs, as another user, with or without committing (rollback mode), and see every element's values.
  • Flow tests (record-triggered flows): define the triggering record and assertions, and run them from Flow Builder.
  • Apex tests that perform DML also execute your flows, so flow failures show up in Apex test runs and deployments.
  • Debug logs record flow execution under the Workflow category (FLOW_ELEMENT_BEGIN, FLOW_ELEMENT_ERROR).
  • Paused and failed flow interviews: Setup → Paused And Failed Flow Interviews.

Versions and deployment

  • Every save creates a new version; only one version is active. Running interviews (paused flows, scheduled paths) keep using the version they started on.
  • Deploy flows with change sets, DevOps Center or the CLI (metadata type Flow). In production, flows deploy as inactive unless "Deploy processes and flows as active" is enabled in Process Automation Settings — which then requires test coverage for record-triggered/autolaunched flows.

Best practices

PracticeWhy
No Get/Create/Update/Delete inside a LoopEach iteration costs a query or DML; 101 records in a loop with a Get Records = limit exception.
Use before-save for same-record updatesMuch faster; no extra DML; doesn't re-trigger automation.
Use entry conditionsFlows that don't match never start.
Fault paths on every DML/actionClean errors instead of rollback emails.
Subflows for shared logicOne place to change; smaller flows.
Don't hardcode IDsUse Get Records by DeveloperName, custom metadata, or custom labels.
Name elements clearly and fill in descriptionsFlows are read far more often than they're written.
Know when to switch to ApexComplex logic, heavy volume, or many interacting branches are easier to test and maintain in code. See Which one do I pick?

Migrating Workflow Rules and Process Builder

Setup → Migrate to Flow converts most workflow rules and processes into record-triggered flows. Review each result: combine flows per object, convert same-record field updates to before-save, and test. Deactivate the old automation once the new flow is live.

Approvals

Approval processes (Setup → Approval Processes) define entry criteria, approvers (manager, a user, a queue, a related user field), steps, record locking, and actions on submit, approve, reject and recall. Submit from a button, Flow (Submit for Approval action) or Apex (Approval.process(new Approval.ProcessSubmitRequest())). For multi-stage approvals with parallel approvers and richer UI, use Flow Approval Processes built on Orchestration.
