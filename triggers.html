Triggers

A trigger is Apex that runs before or after records are inserted, updated, deleted or undeleted. Triggers always receive records in batches of up to 200, so every trigger must be written for a list.

The handler pattern

Keep exactly one trigger per object, with no logic in it. It delegates to a handler class, which keeps order predictable and code testable.

Popular open-source frameworks (Kevin O'Hara's sfdc-trigger-framework, the fflib Apex Common domain layer, the Trigger Actions Framework driven by custom metadata) follow the same idea with more features. Pick one per org and use it everywhere.

Recursion control

A trigger that updates records can cause itself (or another trigger that updates back) to fire again. Options, from simplest:

  1. Change detection (above): the second run sees no change and does nothing. The most robust option.
  2. A static set of processed IDs: skip records already handled in this transaction.
  3. Avoid a plain static Boolean "hasRun" flag: with batches over 200 records, the second chunk of 200 would be skipped.

Worked examples

1. Before insert/update: derive a field from the parent

2. Before update: validation that needs a query

3. After insert: create related records

4. After insert/update/delete/undelete: roll up over a lookup

5. Before delete: prevent deletes

6. After update: hand off to async work

Bypass switches

Data migrations and integrations often need automation off. Make it switchable without deployments:

  • Custom permission Bypass_Triggers assigned by permission set to the migration user (checked in the base class above).
  • Hierarchy custom setting with a checkbox per object, so you can turn off one object's triggers for one user.
  • Custom metadata listing active handlers (the Trigger Actions Framework approach).
  • Static bypass in code: TriggerHandler.bypass('AccountTriggerHandler'); before a DML you don't want re-processed.

Triggers vs Flow on the same object

Both run in the same transaction. Before-save flows run before before-triggers; after-save flows run after after-triggers (see order of execution). Mixing them on one object makes behaviour harder to follow — many teams choose one tool per object, or keep complex objects in Apex and simple ones in Flow.
