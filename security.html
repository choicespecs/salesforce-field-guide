Security & sharing

Access is decided in layers. A user must pass every layer to see a value: the org, the object, the field, and finally the specific record.

Profiles, permission sets and groups

Profile

Exactly one per user. Holds login hours and IP ranges, default record types, page layout assignments, default app, and (historically) object, field and system permissions. Best practice now: give everyone a minimal profile and grant access with permission sets.

Permission set

A bundle of object, field, tab, app, Apex class, Visualforce page, custom permission and system permissions. A user can have many. Permissions only add access; nothing in Salesforce's permission model takes access away.

Permission set group

A bundle of permission sets assigned as one — a persona like "Support Agent". A muting permission set inside the group can switch off specific permissions that the included sets would otherwise grant.

Custom permission

A named on/off flag you create (e.g. Bypass_Validation, Approve_Discounts) and grant through permission sets. Check it in formulas ($Permission.Approve_Discounts), Flow, Apex (FeatureManagement.checkPermission('Approve_Discounts')) and LWC (@salesforce/customPermission/Approve_Discounts).

Permission set licence

Unlocks add-on features (e.g. CPQ, Field Service). Must be assigned before the permission set that uses it.

System permissions View All Data and Modify All Data do the same across every object. Reserve them for admins and a few integration users.

Org-wide defaults (OWD)

Setup → Sharing Settings. The OWD is the baseline record access for users who don't own the record. Set it to what the most restricted user should have, then open up with the tools below.

There are separate internal and external defaults; external (Experience Cloud users) can be the same or more restrictive. Grant Access Using Hierarchies is always on for standard objects and can be switched off for custom objects.

Role hierarchy

Users above someone in the role hierarchy get the same access to that person's records (and, by default, to records shared with them). Roles model data visibility, not the org chart — keep the hierarchy as flat as your visibility needs allow, since deep hierarchies slow down sharing recalculation.

Public groups are the building block for most sharing rules: a named set of users, roles, roles-and-subordinates and other groups.

Implicit sharing

  • Parent implicit: if you can see a Contact, Opportunity or Case, you get read access to its Account.
  • Child implicit: the Account owner gets access to the account's child records, at the level set on the owner's role ("Opportunity Access", "Case Access", "Contact Access").
  • Master-detail children always inherit from the master.

Restriction and scoping rules

Restriction rules work in the opposite direction from sharing: even if sharing grants access, the user only sees records matching the rule's criteria. Example: contractors see only Tasks where Type = 'Contractor'. Available on custom objects, contracts, events, tasks, time sheets and a few others.

Scoping rules set a default filter on what users see in list views, search and lookups (e.g. "my region's accounts") without removing access.

Apex managed sharing

For custom objects, define an Apex Sharing Reason (Object Manager → the object → Apex Sharing Reasons) so your shares survive owner changes and are identifiable. Then insert share rows.

Standard objects use their own share objects (AccountShare, OpportunityShare, CaseShare) with object-specific access fields, and only the Manual row cause.

Debugging "I can't see it"

  1. Is the field on the page? Page layout or Dynamic Forms visibility rule. Not security, but the most common cause.
  2. Licence: does the user's licence include the object?
  3. Object access: Setup → Users → the user → View Summary (on the permission set assignments) shows the combined effect of profile + permission sets for each object and field.
  4. Field-level security: same summary, or Object Manager → field → Set Field-Level Security.
  5. Record access: on the record, Sharing → View Sharing Hierarchy shows who has access and why. Or query UserRecordAccess:
  1. Restriction rules filtering it out?
  2. Test as them: Setup → Users → Login (requires "Administrators Can Log in as Any User" in Login Access Policies).

Org-level security

  • Multi-factor authentication is required for UI logins. SSO via SAML or OpenID Connect can satisfy it.
  • Session settings: timeout, lock sessions to IP, require HttpOnly, clickjack protection.
  • Network access: trusted IP ranges (skip identity verification) vs login IP ranges on the profile (block logins from elsewhere).
  • Health Check (Setup → Health Check) scores settings against Salesforce's baseline.
  • Setup Audit Trail, Login History, field history tracking, and (with Shield) Event Monitoring and Field Audit Trail give you an audit record.
  • Shield Platform Encryption encrypts data at rest at the field and file level with tenant-managed keys.
