Formulas & validation rules

The same Excel-like formula language powers formula fields, validation rules, default values, Flow formulas, report formulas and approval criteria. Learn it once, use it everywhere.

Syntax basics

  • Fields by API name: Amount, Discount__c. Parent fields with dots: Account.Industry, Invoice__r.Status__c.
  • Operators: + - * / ^, & (concatenate text), = == != <> < > <= >=, && and || (or the functions AND(), OR()).
  • Text in double quotes: "Closed Won". Comments: /* like this */.
  • Picklists can't be compared directly: use ISPICKVAL(StageName, "Closed Won") or TEXT(StageName) = "Closed Won".
  • Global variables: $User.Id, $User.Department, $Profile.Name, $UserRole.Name, $Permission.My_Custom_Permission, $Organization.Name, $Setup.My_Setting__c.Field__c, $CustomMetadata.Type__mdt.Record.Field__c, $Label.My_Label.
  • Blank handling: number formulas can treat blank fields as zero or as blank (an option on the formula field). BLANKVALUE(field, default) makes it explicit.
  • Limits: 3,900 characters of formula text and 5,000 bytes compiled size (formulas that reference other formulas count their compiled size too).

Formula field examples

Formula fields are calculated when read. They don't fire triggers or flows when their value "changes", they can't be indexed (unless deterministic and approved by Salesforce support), and cross-object formulas add query cost. If you need to trigger automation or filter big tables on a value, store it in a real field with Flow or Apex.

Validation rules

A validation rule is a formula that returns true when the data is invalid. When it's true, the save fails with your error message, shown at the top of the page or next to a field.

When they run

On every save — UI, API, Apex, Flow, Data Loader — after before-triggers (see order of execution).

What they can use

The record's fields, parent fields, ISNEW(), ISCHANGED(), PRIORVALUE(), $User, $Permission, VLOOKUP, REGEX.

What they can't do

Look at child records, query, or check other records being saved in the same batch. Use Apex for that.

Examples

Validation rule best practices

  • Write the error for the user: say what to do, not what's wrong. "Enter a loss reason before closing the opportunity as lost."
  • Put the error on the field the user needs to fix when there is one.
  • Add a bypass: NOT($Permission.Bypass_Validation) with a custom permission assigned to integration and data-migration users via a permission set. Much cleaner than checking profile names.
  • Mind data loads: activating a new rule doesn't check existing records, but the next edit of any old record will fail if it's invalid.
  • Test with Apex: validation rules fire in tests, so test data must satisfy them. Keep a test data factory up to date.
