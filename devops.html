DevOps & the sf CLI

Modern Salesforce development keeps metadata in Git, builds in sandboxes or scratch orgs, and deploys with the sf CLI from a pipeline.

  • Each developer works in their own sandbox or scratch org.
  • Pull requests trigger a validation deploy (check-only, with tests) against an integration org.
  • Merges deploy to QA, then UAT; releases go to production after sign-off.
  • Keep sandboxes in sync by back-promoting production changes and refreshing regularly.

Deleting metadata

Deploying source never deletes anything by itself. Use a destructive changes manifest:

A GitHub Actions pipeline

For large repos, deploy only what changed with the community sfdx-git-delta plugin (sf sgd source delta --from origin/main --to HEAD --output-dir delta), which generates package.xml and destructiveChanges.xml from the Git diff. Add static analysis with Salesforce Code Analyzer (sf code-analyzer run), which wraps PMD, ESLint and others.

Unlocked packages

Dependencies between packages are declared in sfdx-project.json. Removing a component from a new package version deletes it (or deprecates it) on upgrade.

Things that don't deploy cleanly

  • Data: records, custom setting values, users. Seed them separately.
  • Profiles: retrieving a profile only includes permissions for the other components in the same retrieve. Prefer permission sets.
  • Some settings (e.g. email deliverability, certain org preferences) must be set manually or with post-deploy scripts.
  • Active flows in production deploy inactive unless enabled in settings (see Flow).
  • Field type changes and deletions on fields used by Apex or flows fail until references are removed.
  • Picklist values deploy but don't remove values from existing records.
