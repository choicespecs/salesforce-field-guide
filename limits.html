Governor limits & performance

Every transaction gets a fixed budget. Exceed any of it and Salesforce throws System.LimitException, which can't be caught, and rolls back the entire transaction.

Flows count against the same limits: each Get Records is a SOQL query, each Create/Update/Delete is a DML statement. Managed packages have their own separate SOQL/DML/CPU counters per namespace (CPU and heap are shared).

Bulkification

A trigger, flow or invocable action receives up to 200 records at once. Code must use a constant number of queries and DML statements regardless of how many records arrive.

Pattern: collect → query once → map → loop → DML once

Pattern: avoid nested loops with maps

Pattern: query parent and children together

Checking limits at runtime

Every debug log ends with a LIMIT_USAGE_FOR_NS block showing usage for the transaction. The Apex Log Analyzer extension for VS Code turns logs into flame charts showing where CPU time went.

Selective queries and indexes

On large objects (hundreds of thousands of rows or more), the query optimiser only uses an index when the filter is selective. Non-selective queries in triggers on big objects fail with Non-selective query against large object type.

Indexed fields

  • Standard: Id, Name, OwnerId, CreatedDate, SystemModstamp, RecordTypeId, lookup and master-detail fields, Email on contacts and leads.
  • Custom fields marked External ID or Unique.
  • Custom indexes Salesforce Support adds on request (including some deterministic formula fields).

Selectivity thresholds

IndexSelective if the filter returns fewer than…
Standard index30% of the first million records + 15% of the rest, up to 1,000,000 rows
Custom index10% of the first million + 5% of the rest, up to 333,333 rows

What defeats an index

  • !=, NOT IN, NOT LIKE, EXCLUDES
  • Leading wildcards: LIKE '%smith'
  • Comparing to null on most fields (Field__c = null)
  • Non-deterministic formula fields
  • OR conditions where any branch is non-selective

Use the Query Plan tool (Developer Console → Help → Preferences → Enable Query Plan) to see the cost and which index would be used. A cost under 1 means selective.

Large data volumes

  • Archive old records (to Big Objects, an external store, or Salesforce Archive) so working tables stay small.
  • Skinny tables (via Support) hold frequently used fields from an object in one table, avoiding joins.
  • Bulk API 2.0 for loads and extracts; PK chunking for very large extracts.
  • Defer sharing calculations (via Support) during big ownership or role changes.
  • Load in parent-first order and sort child CSVs by parent ID to reduce lock contention.

Data skew

Account (parent) skew

More than about 10,000 child records under one parent (e.g. a catch-all "Unknown Customer" account). Updating children locks the parent, causing UNABLE_TO_LOCK_ROW errors and slow sharing recalculation. Spread children across several parents.

Ownership skew

One user owning more than about 10,000 records of an object (often an integration user). Role or group changes trigger huge sharing recalculations. Put such users in a role at the top of the hierarchy or with no role, and spread ownership.

Lookup skew

Many records pointing to one lookup target (e.g. every case referencing one "Default" product). Similar locking problems on insert.

CPU time tips

  • Exit early: check if anything relevant changed before doing work.
  • Use maps and sets, not nested loops or List.contains in loops.
  • Reduce describe calls; cache them in statics.
  • Let the database filter: add WHERE clauses rather than filtering in Apex.
  • Consolidate automation: ten record-triggered flows on one object each add overhead.
  • Move non-urgent work async (queueable, async flow path, platform events).
  • Time spent waiting on the database and callouts doesn't count toward CPU time — Apex code, formulas and flow processing do.
